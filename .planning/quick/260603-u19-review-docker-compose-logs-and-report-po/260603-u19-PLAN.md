    ## Issues Found

    ### I-01: ProcessingLogger SurrealDB `$rid` Syntax Bug — CRITICAL

    **Affected:** worker
    **Service logs** show repeated errors:
    ```
    ProcessingLogger: write failed for document <id>: Parse error: Unexpected token `$param` expected a record-id key
     --> [1:27]
    1 | UPDATE document_event_log:$rid CONTENT { document: $doc, step_name: $step, se...
      |                           ^^^^ Record-id's can be create from a param with `type::record("document_event_log",$rid)`
    ```

    **Root cause:** `processing_log.py:118` uses `UPDATE document_event_log:$rid` where `$rid` is a parameter variable. SurrealDB 3.x only allows the `table:literal_id` colon syntax when the ID is a literal — parameter variables require `type::record("document_event_log", $rid)`.

    **Impact:** ALL processing log writes fail silently (caught by the `except Exception` handler at line 137, which only logs a warning). Per-document audit logs are never persisted. The `GET /documents/{id}/logs` endpoint returns empty results.

    **Fix needed:** Replace line 118 in `processing_log.py`:
    ```python
    "UPDATE document_event_log:$rid"  →  "UPDATE type::record('document_event_log', $rid)"
    ```

    **Severity:** HIGH — data loss for audit trail feature, breaks Phase 15 deliverable.

    ### I-02: LLM API Returns Empty Content — MEDIUM

    **Affected:** worker (OpenRouter integration)
    **Service logs** show:
    ```
    LLM API empty content
    RuntimeError: OpenRouter returned empty content in the first choice
    Completing activity as failed ...
    ```

    **Root cause:** For document `3aafb0a5a489445b92aaf086eaf6bf60` ("48- ESMA II fundamentos.pdf"), the OpenRouter API returned a response with no content in the first `choices[0]` element. The `_parse_choice` method at `llm.py:585` raises a `RuntimeError` when this happens.

    **Impact:** Document processing fails completely — the Temporal workflow marks the workflow as failed after `max_attempts=3`. The document stays in `processing` status and cannot be queried. Additionally, the SurrealDB storage has no persist, meaning all data is in-memory.

    **Mitigation possibilities (noted, not actioned in this review):**
    - Add retry with backoff for empty content responses (different from activity-level retry)
    - Log the raw API response for debugging
    - Consider falling back to a different model on empty response

    **(Minor note: The schema-init and bucket-init exited before capturing the LLM failure, so documents were created but never completed.)**

    ### I-03: SurrealDB Running In-Memory (No Persist) — MEDIUM

    **Affected:** surrealdb
    **Service logs** show:
    ```
    INFO surrealdb::core::kvs::mem: Storage mode: in-memory only (no persist path)
    ```
    **Root cause:** `docker-compose.yml` mounts `surrealdb_data:/data` as a volume, but the SurrealDB `start` command does not use `--path /data`. The default is in-memory storage.

    **Impact:** ALL data is lost when the container restarts. This includes documents, events, references, canonical entities, and processing logs. Since the ProcessingLogger bug (I-01) already prevents log writes, even if fixed the data would not survive restart.

    **Fix needed:** Change the SurrealDB command in `docker-compose.yml` from:
    ```yaml
    command: start -u root -p root
    ```
    to:
    ```yaml
    command: start --path /data -u root -p root
    ```

    ### I-04: MinIO Default Credentials Warning — LOW

    **Affected:** minio
    **Service logs** show:
    ```
    WARN: Detected default credentials 'minioadmin:minioadmin'
    ```
    **Root cause:** `docker-compose.yml` uses default `minioadmin:minioadmin` credentials (via `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` env vars with no override).

    **Impact:** Low — this is an internal Docker network with no external exposure. Acceptable for development.
