### I-01: ProcessingLogger SurrealDB `$rid` Syntax Bug — CRITICAL

**Affected:** worker

**Service logs** show repeated errors (>20 occurrences for document `3aafb0a5a489445b92aaf086eaf6bf60`):

```
ProcessingLogger: write failed for document 3aafb0a5a489445b92aaf086eaf6bf60: Parse error: Unexpected token `$param` expected a record-id key
 --> [1:27]
  |
1 | UPDATE document_event_log:$rid CONTENT { document: $doc, step_name: $step, se...
  |                           ^^^^ Record-id's can be create from a param with `type::record("document_event_log",$rid)`
```

**Root cause:** `processing_log.py:118` uses `UPDATE document_event_log:$rid` where `$rid` is a SurrealQL parameter variable. SurrealDB 3.x requires the `type::record()` function to create a record ID from a parameter — the `table:literal_id` colon syntax only works with literal values, not bound parameters.

**Impact:** ALL processing log writes fail silently. The `except Exception` handler at line 137 catches the SurrealDB parse error and logs a `WARNING` level message, but the entry is never persisted. Per-document audit logs (Phase 15 deliverable) are completely non-functional. The `GET /documents/{id}/logs` endpoint returns empty results.

**Logs confirm this error fires for every single workflow step that calls `ProcessingLogger.log()`.** Each document processing run generates 10-20 repeated error entries in the worker logs — this is not a transient issue.

**Fix needed:** Replace line 118 in `processing_log.py`:
```python
"UPDATE document_event_log:$rid"  →  "UPDATE type::record('document_event_log', $rid)"
```

**Severity:** HIGH — Complete data loss for audit trail feature. Breaks Phase 15 deliverable (`per-document-processing-logs`). Blocks validation of all Temporal processing steps.

### I-02: LLM API Empty Content Response — MEDIUM

**Affected:** worker (OpenRouter integration)

**Service logs** show a complete failure trace for document `3aafb0a5a489445b92aaf086eaf6bf60`:

```
LLM API empty content
Completing activity as failed ({'activity_id': '7', 'activity_type': 'extract_events_activity', 'attempt': 1, ...})
Traceback (most recent call last):
  ...
  File "/app/src/eth_pipeline/llm.py", line 585, in _parse_choice
    raise RuntimeError(msg)
RuntimeError: OpenRouter returned empty content in the first choice
```

**Root cause:** The OpenRouter API returned a response with no content in `choices[0]` for the PDF document "48- ESMA II fundamentos.pdf". The `_parse_choice` method at `llm.py:585` raises a `RuntimeError` when `choices[0].message.content` is empty or missing. The Temporal activity completes as failed after the first attempt — there is no retry-with-backoff for this specific condition (only activity-level `max_attempts=3`, which retries the same problematic call).

**Impact:** Document processing fails completely for this document. With `max_attempts=3`, the workflow retries but will fail all 3 attempts and leave the document in a terminal `failed` state. The document becomes unprocessable without manual intervention.

**Mitigation possibilities (noted, not actioned in this review):**
- Add a retry-with-backoff for empty content responses (separate from activity-level retry, which retries the same failing call)
- Log the raw API response for debugging
- Consider falling back to a different model when the primary model returns empty content
- Mark workflow as `failed` with a structured error rather than leaving the document in indeterminate state

### I-03: SurrealDB Running In-Memory Only (No Persist) — MEDIUM

**Affected:** surrealdb

**Service logs** confirm:

```
2026-06-02T14:26:56.135944Z  INFO surrealdb::core::kvs::ds: Starting kvs store in memory
2026-06-02T14:26:56.138163Z  INFO surrealdb::core::kvs::mem: Storage mode: in-memory only (no persist path)
```

**Root cause:** `docker-compose.yml` mounts `surrealdb_data:/data` as a volume (line 8), but the SurrealDB start command does not use `--path /data`. The default is in-memory storage.

```
services:
  surrealdb:
    command: start -u root -p root      # ← Missing --path /data
    volumes:
      - surrealdb_data:/data            # ← Volume exists but is unused
```

**Impact:** ALL data is lost when the container restarts. This includes:
- Documents, events, references, and canonical entities
- Processing logs (even if I-01 were fixed)
- Schema definitions (re-applied via schema-init on restart, but data is gone)

Since the SurrealDB container has been running for 34 hours, this also means:
- If a restart happens, ALL data accumulated during v4.0 testing is lost
- Any data the integration tests processed is ephemeral
- The volume `surrealdb_data` exists on disk but is never written to — it remains empty

**Fix needed:** Change the SurrealDB command in `docker-compose.yml` from:
```yaml
command: start -u root -p root
```
to:
```yaml
command: start --path /data -u root -p root
```

**Severity:** MEDIUM (HIGH when combined with I-01 — even if the logger bug is fixed, data still won't survive restart)

### I-04: MinIO Default Credentials Warning — LOW

**Affected:** minio

**Service logs** show:

```
WARN: Detected default credentials 'minioadmin:minioadmin', we recommend that you change these values with 'MINIO_ROOT_USER' and 'MINIO_ROOT_PASSWORD' environment variables
```

**Root cause:** `docker-compose.yml` uses default `minioadmin:minioadmin` credentials (via `MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD` env vars with no override). The environment variables are set as:
```yaml
MINIO_ROOT_USER: ${MINIO_ROOT_USER:-minioadmin}
MINIO_ROOT_PASSWORD: ${MINIO_ROOT_PASSWORD:-minioadmin}
```
No `.env` override is configured.

**Impact:** LOW — this is an internal Docker network with no external exposure. The only consumers are the API and worker services, both on the `eth-pipeline` internal network. Running with default creds is a valid development choice, but should be hardened before any non-development deployment. The Cloudflared tunnel (I-06) may expose the web UI but does not expose MinIO.

**Affected:** integration-tests (exit code 1)

   - Expected: `0` orphaned `document_chunk` records after DELETE
   - Actual: `1` orphaned chunk remaining
   - Error: `DELETE should leave zero orphaned document_chunks — 1 !== 0`

2. **Test 5: Chunk transparency — full text reconstruction** (`pipeline_v2.test.js:228`)
   - Expected: `0` `document_chunk` records for text-path documents
   - Actual: `1` chunk record remains

**Root cause:** The DELETE endpoint at `/documents/{id}/events` may not be cascading deletes to `document_chunk` records. Text-path documents are expected to have zero chunk records (the full text is passed directly to `extract_events_activity`), but a single chunk remains after processing.

**Impact:** LOW — these are assertion tests for a cleanup edge case and a transparency invariant. They do not affect core pipeline functionality (event extraction, entity resolution, search). The failures suggest a minor gap in the DELETE cascading logic or a chunk cleanup inconsistency.

**Also noted:** A TypeScript compilation error in `pipeline_v4.test.ts:776`:
```

```
This is a type error in the test file — the `_parse_count` return type may be `number | { value: number }` but accessing `.value` on a plain `number` is invalid. This mirrors the same pattern in `processing_log.py:_parse_count`. The tests compile with `npx tsc` but produce a type error.
