<objective>
Add basic passcode-based permissions to the internet-exposed eth-pipeline system.

Purpose: The system is exposed via a Cloudflare tunnel; mutating actions (load documents, add providers, delete) must be gated by passcodes while reading stays open. The UI must stay consistent: anything a visitor cannot do is hidden until the right passcode is entered.

Output: Server-side passcode service + decorator + check endpoint, protected mutating endpoints, passcode modal + gating in index.html and providers.html, passcode.png committed to static assets, unit tests.

Locked decisions from the task description (treated as D-01..D-06):
- D-01: Default view = documents view (not the loading/upload view).
- D-02: Gear (providers) is level A; passcode is an obligatory parameter on changing endpoints; server-side check is a decorator; UI remembers the passcode in localStorage and does not re-ask when correct.
- D-03: Check endpoint validates a passcode and returns its level (A, B, C).
- D-04: No passcode → load document control hidden, all non-reading actions hidden.
- D-05: Level A allows add providers + send documents but NOT deletes; delete buttons remain visible but ask for passcode B.
- D-06: Level C is READ, asked the first time. Passcodes come from env (PASSCODE_A/B/C) with hardcoded defaults AAAAA/BBBBB/CCCCC. Comparison constant-time (hmac.compare_digest); wrong passcode never leaks level info. Modal: passcode.png + input labeled with the level letter, matching existing input width style, slightly bigger font, no extra chrome.
</objective>

Create `src/eth_pipeline/passcodes.py`:
- Read levels from env at verify time (not import time) with hardcoded defaults per D-06: `os.environ.get("PASSCODE_A", "AAAAA")`, `PASSCODE_B` → "BBBBB", `PASSCODE_C` → "CCCCC".
- `LEVELS = {"A", "B", "C"}`.
- `verify_passcode(code: str, level: str) -> bool`: constant-time via `hmac.compare_digest` comparing the supplied code against the requested level's value. No logging of passcodes.
- `resolve_level(code: str) -> str | None`: returns "A"/"B"/"C" if the code matches that level's value (compare_digest), else None. Never raises, never reveals which level a near-miss belonged to (D-06).
- Decorator `require_passcode(level)` implementing D-02: wraps an async route handler; the wrapped function's signature must expose `passcode: str` as a REQUIRED FastAPI query parameter (annotate the wrapper with `passcode: str = Query(...)` so FastAPI injects it and OpenAPI shows it as obligatory — do NOT read it from request.state or headers). Behavior: missing/empty passcode → HTTP 403 with a generic detail ("Passcode required."); wrong passcode for the declared level → HTTP 403 with the SAME generic detail regardless of whether the code is valid for another level (D-06: no level leakage). Use `functools.wraps`.

Create `src/eth_pipeline/api/routes/passcodes.py` implementing D-03: router with `GET /api/passcode/check`, query param `passcode: str`. Returns `{"level": "A"|"B"|"C"}` when `resolve_level` matches; HTTP 401 with generic detail when no level matches. No other fields in the response.

Protect the mutating endpoints (per D-02/D-05, each endpoint requires exactly its own level — A does NOT imply B):
- documents.py: POST /documents → require_passcode("A"); POST /documents/upload → require_passcode("A"); DELETE /documents/{document_id} → require_passcode("B").
- providers.py: POST /api/providers → require_passcode("A"); POST /api/providers/{provider_id}/test → require_passcode("A"); DELETE /api/providers/{provider_id} → require_passcode("B").
All GET endpoints stay open (D-04: reading needs nothing).

Register the passcodes router in `api/__init__.py` alongside the other routers. Add PASSCODE_A/PASSCODE_B/PASSCODE_C lines (with the default values commented as fallbacks) to `.env.example` — docker-compose already passes `.env` via env_file, so no compose change.

Create `tests/test_passcodes.py` as pure unit tests (no DB, no stateful fixtures so `./test.sh --unit` picks them up), monkeypatching env vars:
- defaults: without env vars, "AAAAA"/"BBBBB"/"CCCCC" resolve to A/B/C respectively
- env override: PASSCODE_A=ZZZZZ makes "AAAAA" fail and "ZZZZZ" succeed for level A
- wrong passcode: `resolve_level` returns None and `verify_passcode` is False; a code valid for level A must NOT satisfy require_passcode("B") (assert 403)
- missing passcode on a protected handler → 403; check endpoint: correct code → 200 with level, wrong code → 401 with no level info in the detail/body
Exercise the decorator + check endpoint through a small FastAPI app or direct calls — no dev-DB contact.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| internet → API | The app is exposed via Cloudflare tunnel; all endpoints are reachable by strangers |
| browser UI → API | UI-held passcodes (localStorage) travel as query params on each mutating call |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-JD7-01 | Spoofing | mutating endpoints without passcode | high | mitigate | `require_passcode` decorator on all six mutating endpoints; passcode is an obligatory query param (Task 1) |
| T-JD7-02 | Info disclosure | level leakage on failure | medium | mitigate | uniform generic 403/401 detail; `resolve_level` returns None with no per-level signals; compare_digest for all comparisons (Task 1) |
| T-JD7-03 | Info disclosure | passcodes in URLs (access logs, history) | medium | accept | Query param chosen for uniformity across JSON and multipart endpoints; internal deployment, low-value secrets; UI never logs them |
| T-JD7-04 | Tampering | npm/CDN supply chain | low | accept | No new external dependencies added; UI uses inline JS and one local image only |
| T-JD7-05 | Elevation of privilege | A-holder attempting deletes | medium | mitigate | Level A does not satisfy the B decorator — verified by unit test (Task 1) |
</threat_model>
