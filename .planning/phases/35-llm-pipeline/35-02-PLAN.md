       - Signature: `async def resolve_references_v7_activity(document_id: str) -> dict`
       - Initialize `params = _db_params()` and `_log = ProcessingLogger(params)`
       - Log activity start: `activity.logger.info("resolve_references_v7_activity called [document_id=%s]", document_id)`

    4. **Step 1 — Fetch all event_refs for the document**:
       ```sql
       SELECT er.id, er.verbatim_text, er.span_start, er.span_end,
              er.chunk_index, er.event_id
       FROM event_ref er
       JOIN event_document ed ON er.event_id = ed.event_id
       WHERE ed.document_id = $1
       ORDER BY er.chunk_index, er.id
       ```
       Use `_extract_query_results()` to convert to list[dict].

    5. **Step 2 — Fetch chunks for offset lookup**:
       ```sql
       SELECT chunk_index, text, offset_start, offset_end
       FROM document_chunk
       WHERE document = $1
       ORDER BY chunk_index ASC
       ```
       Build `chunk_map` dict: `{row['chunk_index']: row}`

    6. **Step 3 — For each ref, locate verbatim_text in chunk and compute absolute offsets**:
       - Get `chunk = chunk_map.get(ref['chunk_index'])`; continue if None
       - Exact match: `pos = chunk['text'].find(ref['verbatim_text'])`
       - Case-insensitive fallback (if pos == -1): `match = re.search(re.escape(ref['verbatim_text']), chunk['text'], re.IGNORECASE)`; if match, `pos = match.start()`
       - If still -1: log `activity.logger.warning(...)` with chunk_index, ref id, and first 80 chars of verbatim_text; continue to next ref (ref left with LLM's approximate offsets)
       - Compute document-absolute offsets: `doc_span_start = chunk['offset_start'] + pos`, `doc_span_end = doc_span_start + len(ref['verbatim_text'])`
       - UPDATE: `UPDATE event_ref SET span_start = $1, span_end = $2 WHERE id = $3`, [doc_span_start, doc_span_end, ref['id']]
       - Increment `resolved` counter

    7. **Return dict**: `{"document_id": document_id, "resolved": resolved, "total": len(refs)}`

    8. **Error handling**: same pattern as resolve_entities.py — `except ConnectionError` and `except Exception` with full logging

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| LLM output → Database | Extracted event data (title, description, location, participants, verbatim_text) is written to PostgreSQL. All values are LLM-generated text. |
| Document text → Offset computation | Chunk text read from document_chunk is searched for verbatim_text spans using str.find() — no injection surface. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-35-07 | Tampering | SQL injection via event field values | mitigate | All INSERT and UPDATE statements use asyncpg parameterized queries (`$1, $2, ...`). LLM-generated strings are NEVER interpolated into SQL. This is the existing pattern from store_extraction_results.py. |
| T-35-08 | Tampering | Wrong DELETE scope wipes all document events | mitigate | The DELETE is scoped to chunk_index via the event_document join: `WHERE id IN (SELECT event_id FROM event_document WHERE document_id = $1 AND chunk_index = $2)`. The test test_per_chunk_isolation verifies this scope. If the executor mistakenly uses document-level DELETE, that test MUST fail. |
| T-35-09 | Denial of Service | Large verbatim_text causes CPU exhaustion in str.find() | accept | str.find() is O(n) in chunk text size (~512KB max). This is a bounded operation. Case-insensitive regex fallback adds a constant overhead. Accepted risk: no practical DoS vector from a 512KB string search. |
| T-35-10 | Information Disclosure | event_ref.verbatim_text stored in plaintext | accept | The event_ref table stores exact document text spans — this is its purpose. No encryption at rest is required for a single-user research tool. Accepted risk level: low. |
| T-35-11 | Elevation of Privilege | CASCADE delete bypassing authorization | accept | Single-user research tool with no auth system. DELETE operations are initiated by the Temporal workflow, not by user-facing API. No privilege escalation surface exists. |
</threat_model>
