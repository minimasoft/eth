  <name>Task 2: Create pipeline_v4.test.ts with 4 test groups</name>
  <files>
    tests/integration/pipeline_v4.test.ts

  <action>
    Create `tests/integration/pipeline_v4.test.ts` following the established pattern from `e2e_pipeline.test.ts`, `pipeline.test.ts`, and `pipeline_v2.test.ts`.

    **File structure:**
    - Imports: `describe, it, after` from `node:test`, `assert` from `node:assert/strict`, helpers from `./helpers.js`
    - Inline test data constants for the two new fixtures (embed the text, don't read from disk — same pattern as e2e_pipeline.test.ts does for SAMPLE_CRIMINAL_CASE)
    - Test state: `testDocIds` array, `after()` cleanup calling `cleanupTestDocuments()`
    - `waitForProcessing()` helper (same pattern as e2e_pipeline.test.ts — polls status with 120s timeout, 2s intervals, degraded-mode tolerance)
    - `sqlExecute()` helper for direct SurrealDB SQL queries (same pattern as 13-schema-evolution.test.ts)
    - All tests wrapped in `skipIfDegraded(${API_BASE}/health, ...)` — graceful degradation when Temporal/LLM unavailable

    **Test Group 1: Offsets**
    - Submit `sample_multi_page_document.txt` (the one with page markers)
    - Wait for processing
    - Query references via GraphQL with fields: `id pageNumber pageOffsetStart pageOffsetEnd referenceType verbatim_text`
    - Assert that at least some references have non-null `pageNumber` (per D-017: deterministic computation from chunk metadata)
    - Assert that references mentioning text on page 1 have `pageNumber: 1`, page 2 references have `pageNumber: 2`, etc.
    - Support fallback: if GraphQL doesn't expose the fields, verify via direct SurrealDB SQL query `SELECT page_number, page_offset_start, page_offset_end FROM reference WHERE ...`
    - Log the count of references with populated offsets vs total references

    **Test Group 2: Processing Logs**
    - Submit a short document (e.g., civil case or criminal case snippet)
    - Wait for processing (tolerate degraded/pending)
    - Call `GET /documents/{id}/logs` via REST
    - Assert HTTP 200 response
    - Parse response: verify it's an array of log entries (could be empty if processing didn't complete)
    - If entries exist: verify each entry has fields: `step_name` (string), `severity` (one of info/warning/error), `message` (string), `created_at` (string)
    - Log the count and severity distribution
    - Fallback: if endpoint returns 404 or empty, log informative message (per LOGS-06 the endpoint was added in Phase 15)

    **Test Group 3: Event Entities**
    - Submit `sample_criminal_case.txt`
    - Wait for processing
    - Query canonical entities via GraphQL with filter or all, check for `entity_type === 'event'`
    - Use `sqlExecute` to run: `SELECT * FROM canonical_entity WHERE entity_type = 'event' LIMIT 5;`
    - Assert at least one event-type canonical entity exists (or log message if processing didn't complete — degraded tolerance)
    - If event entities found: verify they have `properties` object with expected keys (time_range, location, participants, que_paso, title — per EVNT-02)
    - Log event entity count and sample properties

    **Test Group 4: Search-First Resolution**
    - Submit `sample_criminal_case.txt`
    - Wait for processing
    - Query references via GraphQL with fields: `id entity_id { id } verbatim_text reference_type`
    - Assert that at least some references have non-null `entity_id` (per D-022: the entity_id field carries pre-resolved links)
    - Fallback: use `sqlExecute` to query `SELECT entity_id, verbatim_text FROM reference WHERE entity_id IS NOT NULL LIMIT 10;`
    - If entity_id references exist: check that entity_id links to an existing canonical_entity (resolvable)
    - Log entity_id coverage: e.g., "X/Y references have entity_id populated"

    **Assertion philosophy (following project patterns):**
    - Use strict assertions where possible (`assert.equal`, `assert.ok`)
    - `assertGraphqlOk` for GraphQL response validation
    - `assertNonNull` for nullable values
    - Degraded-mode tolerance: if Temporal/LLM aren't running, log "ℹ" messages and skip assertions gracefully — the test verifies the API shape works even when processing can't complete
    - Never use `assert.fail` for infrastructure-dependent conditions

    **Cleanup:**
    - Use the same `cleanupTestDocuments()` pattern: `httpDelete` for each test doc
    - Delete any SQL-created test records for event entity and reference tests
  </action>
