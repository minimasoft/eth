## Summary

Phase 33 is the foundational schema phase for the v7.0 event-centric rewrite. It must create 5 new PostgreSQL tables (`event_v2`, `event_location`, `event_participant_v2`, `event_document`, `event_ref`) alongside existing tables (additive-only, no drops), add a `schema_version` column to the `document` table, enable the PostGIS extension, and install Alembic migration tooling for schema versioning going forward.

The project currently uses raw SQL via `schema.sql` + `init_schema.py` with no migration system. This phase introduces Alembic (1.18.4+) with async support, SQLAlchemy 2.0.50 for model definitions, and the `async` Alembic template for compatibility with the existing `asyncpg` connection pool (`/home/u/src/eth/src/eth_pipeline/db.py`). PostGIS extension is enabled via `CREATE EXTENSION IF NOT EXISTS postgis` in the initial migration. All new FK relations use `ON DELETE CASCADE`. The `document` table gets a `schema_version` column defaulting to `'v6'` as a feature flag.

The initial Alembic migration must be a **manual migration** (not autogenerated) that stamps the existing schema as the "base" and then applies the v7.0 additions. The existing `init_schema.py` script will still create the base schema for new deployments.

**Primary recommendation:** Use Alembic's built-in `async` template for the migration environment. Write a single initial migration that (1) creates the `alembic_version` table and stamps the base, (2) enables PostGIS, (3) adds `schema_version` to `document`, and (4) creates the 5 new v7.0 tables. Keep `init_schema.py` for greenfield deploys but make it stamp Alembic after running.

### Pattern 2: Manual Initial Migration (Stamp Existing Schema)
**What:** The initial migration is manual (not autogenerated) because it must stamp the existing v6.x schema as the base, then add v7.0 tables. `down_revision` is set to `None`.
**When to use:** When introducing Alembic to an existing database with schema already in place.
**Source:** [CITED: alembic.sqlalchemy.org/en/latest/cookbook.html#building-an-up-to-date-database-from-scratch]

```python
"""v7.0 foundation: PostGIS, schema_version, new tables

Revision ID: 0001
Revises: None
Create Date: 2026-06-09
"""
from alembic import op
import sqlalchemy as sa

revision = '0001'
down_revision = None

def upgrade():
    # Step 1: Enable PostGIS
    op.execute("CREATE EXTENSION IF NOT EXISTS postgis")
    
    # Step 2: Add schema_version to document table
    op.add_column('document', sa.Column(
        'schema_version', sa.String(10),
        server_default='v6',
        nullable=False
    ))
    
    # Step 3: Create event_v2
    op.create_table(
        'event_v2',
        sa.Column('id', sa.String(), primary_key=True),
        sa.Column('document_id', sa.String(), nullable=False),
        sa.Column('title', sa.String(), nullable=False),
        sa.Column('description', sa.Text(), default=''),
        sa.Column('time_start', sa.DateTime(timezone=True), nullable=True),
        sa.Column('time_end', sa.DateTime(timezone=True), nullable=True),
        sa.Column('time_precision', sa.String(), nullable=True),
        sa.Column('extraction_confidence', sa.Float(), default=1.0),
        sa.Column('created_at', sa.DateTime(timezone=True), server_default=sa.func.now()),
        sa.Column('updated_at', sa.DateTime(timezone=True), server_default=sa.func.now()),
        sa.ForeignKeyConstraint(['document_id'], ['document(id)'], ondelete='CASCADE'),
    )
    op.create_index('idx_event_v2_document', 'event_v2', ['document_id'])
    op.create_index('idx_event_v2_time_start', 'event_v2', ['time_start'])
    
    # Step 4: Create event_location
    op.create_table(
        'event_location',
        sa.Column('id', sa.String(), primary_key=True),
        sa.Column('event_id', sa.String(), nullable=False),
        sa.Column('name', sa.String(), nullable=False),
        sa.Column('location_type', sa.String(), nullable=True),
        sa.Column('geom', sa.String(), nullable=True),  # PostGIS geometry as EWKT text
        sa.Column('created_at', sa.DateTime(timezone=True), server_default=sa.func.now()),
        sa.ForeignKeyConstraint(['event_id'], ['event_v2(id)'], ondelete='CASCADE'),
    )
    op.create_index('idx_event_location_event', 'event_location', ['event_id'])
    
    # Step 5: Create event_participant_v2
    op.create_table(
        'event_participant_v2',
        sa.Column('id', sa.String(), primary_key=True),
        sa.Column('event_id', sa.String(), nullable=False),
        sa.Column('name', sa.String(), nullable=False),
        sa.Column('role', sa.String(), default=''),
        sa.Column('confidence', sa.Float(), nullable=True),
        sa.Column('created_at', sa.DateTime(timezone=True), server_default=sa.func.now()),
        sa.ForeignKeyConstraint(['event_id'], ['event_v2(id)'], ondelete='CASCADE'),
    )
    op.create_index('idx_event_participant_v2_event', 'event_participant_v2', ['event_id'])
    
    # Step 6: Create event_document (many-to-many: event ↔ document)
    op.create_table(
        'event_document',
        sa.Column('id', sa.String(), primary_key=True),
        sa.Column('event_id', sa.String(), nullable=False),
        sa.Column('document_id', sa.String(), nullable=False),
        sa.Column('chunk_index', sa.Integer(), nullable=True),
        sa.Column('created_at', sa.DateTime(timezone=True), server_default=sa.func.now()),
        sa.ForeignKeyConstraint(['event_id'], ['event_v2(id)'], ondelete='CASCADE'),
        sa.ForeignKeyConstraint(['document_id'], ['document(id)'], ondelete='CASCADE'),
    )
    op.create_index('idx_event_document_event', 'event_document', ['event_id'])
    op.create_index('idx_event_document_doc', 'event_document', ['document_id'])
    
    # Step 7: Create event_ref
    op.create_table(
        'event_ref',
        sa.Column('id', sa.String(), primary_key=True),
        sa.Column('event_id', sa.String(), nullable=False),
        sa.Column('reference_type', sa.String(), nullable=False),
        sa.Column('verbatim_text', sa.Text(), nullable=False),
        sa.Column('span_start', sa.Integer(), nullable=False),
        sa.Column('span_end', sa.Integer(), nullable=False),
        sa.Column('chunk_index', sa.Integer(), nullable=True),
        sa.Column('created_at', sa.DateTime(timezone=True), server_default=sa.func.now()),
        sa.ForeignKeyConstraint(['event_id'], ['event_v2(id)'], ondelete='CASCADE'),
    )
    op.create_index('idx_event_ref_event', 'event_ref', ['event_id'])

def downgrade():
    op.drop_table('event_ref')
    op.drop_table('event_document')
    op.drop_table('event_participant_v2')
    op.drop_table('event_location')
    op.drop_table('event_v2')
    op.drop_column('document', 'schema_version')
    # NOTE: PostGIS extension is NOT dropped on downgrade (could affect other extensions/db features)
```

### Anti-Patterns to Avoid
- **Running `alembic revision --autogenerate` against the existing v6 database** — Autogenerate would detect the existing tables as "new" and try to recreate them. Instead, create a manual initial migration with `down_revision = None`.
- **Dropping PostGIS in the downgrade** — Other parts of the system may depend on PostGIS. `CREATE EXTENSION IF NOT EXISTS` is idempotent; never drop it.
- **Using `init_schema.py` to also apply v7.0 DDL** — The v7.0 tables must go through Alembic so version tracking is accurate. Keep `init_schema.py` for v6.x base tables only.
- **Installing geoalchemy2** — Unnecessary complexity. The project uses raw SQL via asyncpg; PostGIS geometry/geography types can be stored as EWKT strings and queried via `ST_GeomFromEWKT()`/`ST_AsEWKT()`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Schema version tracking | Custom version table + SQL scripts | Alembic | Alembic handles version table, upgrade/downgrade graph, dependency ordering, autogenerate |
| PostGIS geometry management | Custom geometry parsing library | Raw EWKT/EWKB via asyncpg + PostGIS functions | Simple lat/lon columns need no ORM layer; PostGIS native functions handle all spatial operations |
| Migration idempotency | Check-if-exists logic per migration step | `CREATE TABLE IF NOT EXISTS`, `op.execute()` with idempotent SQL | PostgreSQL DDL supports IF NOT EXISTS; Alembic tracks which migrations ran |

**Key insight:** The most complex part of this phase is Alembic adoption in an existing project. The actual DDL is straightforward (5 new tables, 1 ALTER TABLE, 1 CREATE EXTENSION). The migration environment setup (async env.py, initial stamping, Docker compose integration) is where mistakes happen.

## Common Pitfalls

### Pitfall 1: Autogenerate Includes Existing Tables
**What goes wrong:** Running `alembic revision --autogenerate` for the first migration detects all existing v6.x tables as "new" and generates DDL to create them, duplicating `schema.sql`.
**Why it happens:** Autogenerate compares SQLAlchemy `MetaData` against the live database. If `MetaData` is empty, every table is "new."
**How to avoid:** The initial migration is manual with `down_revision = None`. Only use autogenerate for subsequent migrations after `target_metadata` is populated with SQLAlchemy model classes.
**Warning signs:** Migration file contains `create_table` for `document`, `event`, `reference` — these are existing tables.

### Pitfall 2: Async env.py Not Properly Configured
**What goes wrong:** Alembic migrations fail with "asyncpg requires an async driver" or "cannot use async engine in sync context."
**Why it happens:** The default `env.py` creates a sync engine. The project uses `asyncpg`.
**How to avoid:** Use `alembic init --template async alembic` which generates an async-compatible `env.py` using `AsyncEngine` from `sqlalchemy.ext.asyncio`.
**Warning signs:** Migration fails with "await outside async function" or "coroutine was never awaited."

### Pitfall 3: `schema_version` on Existing `document` Table Has No Default for New Rows
**What goes wrong:** New documents inserted by application code miss the `schema_version` column, causing NOT NULL constraint failures.
**Why it happens:** The `server_default='v6'` is set during migration, but application code must set it explicitly for future inserts.
**How to avoid:** The `schema_version` column definition uses `server_default='v6'` for schema-level default. Application code must set `schema_version='v7'` when creating documents for the new pipeline.
**Warning signs:** `psycopg2.errors.NotNullViolation: null value in column "schema_version"` on document insert.

### Pitfall 4: Docker Compose `schema-init` Service Bypasses Alembic
**What goes wrong:** `docker compose up` runs `init_schema.py` which creates schema.sql tables but never runs Alembic migrations, so v7.0 tables are missing.
**Why it happens:** The existing `schema-init` service runs `python scripts/init_schema.py` directly.
**How to avoid:** Modify `scripts/init_schema.py` to run `alembic stamp head` after creating the base schema. Or create a separate migration step in docker-compose.
**Warning signs:** After docker compose up, `event_v2` table does not exist.

### Alembic Async env.py (generated by `alembic init --template async`)

```python
# Source: [CITED: alembic.sqlalchemy.org/en/latest/tutorial.html]
from asyncio import run
from logging.config import fileConfig

from alembic import context
from sqlalchemy.ext.asyncio import create_async_engine

from eth_pipeline.models.v7_event import Base  # SQLAlchemy models

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = Base.metadata

def run_migrations_offline() -> None:
    """Run migrations in 'offline' mode."""
    url = config.get_main_option("sqlalchemy.url")
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
    )
    with context.begin_transaction():
        context.run_migrations()

def do_run_migrations(connection):
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()

async def run_async_migrations() -> None:
    """Run migrations using async engine."""
    connectable = create_async_engine(
        config.get_main_option("sqlalchemy.url"),
    )
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()

def run_migrations_online() -> None:
    """Run migrations in 'online' mode using async engine."""
    run(run_async_migrations())

if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

## Open Questions

1. **PostgreSQL Docker image: postgis vs postgres**
   - What we know: Current Dockerfile uses `postgres:17-alpine`. The `postgis/postgis:17-3.4-alpine` image is the standard PostGIS-bundled variant.
   - What's unclear: Whether `CREATE EXTENSION postgis` works on bare `postgres:17-alpine`. It requires the PostGIS shared objects to be installed.
   - Recommendation: Change Docker image to `postgis/postgis:17-3.4-alpine` in `docker-compose.yml` to ensure PostGIS libraries are available.

2. **`schema_version` column: data type and default value semantics**
   - What we know: Must track whether documents use old (`v6`) or new (`v7`) schema.
   - What's unclear: Should this default to `'v6'` for existing rows and `'v7'` for documents created by the new pipeline? The answer determines whether existing documents auto-migrate.
   - Recommendation: Default to `'v6'` for safety. Application code explicitly sets `'v7'` when creating documents via the new pipeline. This is consistent with FND-01 (additive-only, no data migration required).
