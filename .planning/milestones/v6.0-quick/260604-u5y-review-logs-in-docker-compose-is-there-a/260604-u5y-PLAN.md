With the record counts from Task 1, analyze the delete_document cascade code at `src/eth_pipeline/api/routes/documents.py:910-1133` against the actual database state:

**Identify which entity types remain and why the cascade didn't clean them:**

1. **Gap 1 — event_entity_link orphans:** The delete cascade (Step 1b, lines 997-1003) deletes `event_entity_link` edges for the document's events, then deletes events (Step 4). But Step 8 only checks canonical entities that were found via `reference.canonical_entity` (lines 1006-1016 `affected_ce_query`). Canonical entities linked ONLY through `event_entity_link` are NEVER checked for orphan status.

2. **Gap 2 — entity_id field ignored:** Step 2 queries `SELECT VALUE canonical_entity FROM reference WHERE event.document = $doc_id AND canonical_entity IS NOT NONE` (lines 1006-1011). But Phase 17 search-first resolution uses `reference.entity_id`, NOT `reference.canonical_entity`. Entities referenced only via `entity_id` will NOT appear in `affected_ce_rids` and are therefore never checked for orphan status.

3. **Gap 3 — cross-document entities:** If canonical entity X is referenced by documents A and B, and you delete document A — Step 8 checks and finds X still has references from B (remaining > 0), so X is kept. Then when you delete document B separately, Step 8 runs again — this time X should have 0 references and be deleted. However, if the reference from B uses `entity_id` instead of `canonical_entity`, gap 2 applies again.

4. **Gap 4 — prior pipeline failures:** The previous quick task (260604-taa) documented pipeline processing failures at `store_extraction_results_activity`. If documents went to `failed` status with partial data (events/entities created but references orphaned), the cleanup script catches orphan references but does NOT clean orphan canonical entities.

Correlate the gap analysis with actual counts to confirm which gaps are active.
