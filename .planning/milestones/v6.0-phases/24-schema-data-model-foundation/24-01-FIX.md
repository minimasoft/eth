## Findings Closed by Architecture Migration (Deferred)

The following findings are against SurrealDB-specific features that do not exist in PostgreSQL. They are **closed by architecture change**, not by code fix.

### DFR-01: CR-01 — event_participant PERMISSIONS missing

**Original issue:** SurrealDB `TYPE RELATION` without `PERMISSIONS` clause defaults to `PERMISSIONS FULL`, exposing graph edge mutations via auto-GraphQL.

**Deferred reason:** PostgreSQL has no auto-GraphQL layer. The `event_participant` table is a standard FK-backed table with no automatic mutation exposure. The security surface is fundamentally different. No code change needed.

**Mitigation intact:** Application code (`store_extraction_results.py:59-63`, `resolve_entities.py:334-337`) is the sole writer of `event_participant` edges. No direct mutation path exists at the SQL level beyond admin access.

### DFR-02: WR-01 — event_participant implicitly SCHEMALESS

**Original issue:** SurrealDB `TYPE RELATION` without `SCHEMAFULL` allows phantom fields.

**Deferred reason:** PostgreSQL `CREATE TABLE` with explicit typed columns (`id TEXT PK`, `in_event TEXT FK NOT NULL`, `out_entity TEXT FK NOT NULL`, `role TEXT NOT NULL`, `confidence REAL`, `created_at TIMESTAMPTZ`) is inherently schema-full. No phantom fields can be written. This is strictly enforced at the database level.

**Evidence:** Lines 98-105 of `schema.sql` define every column with a concrete type. Any attempt to INSERT with extra columns fails with a PostgreSQL column-not-found error.

### DFR-03: IN-01 — FLEXIBLE object fields without ASSERT validation

**Original issue:** `time_window` and `location_point` have no SurrealDB ASSERT to validate field structure.

**Deferred reason:** PostgreSQL chose `JSONB` as the natural equivalent of SurrealDB's `TYPE object | null FLEXIBLE`. JSONB is inherently flexible and accepts any valid JSON. This is an architectural decision, not an oversight — the `FLEXIBLE` modifier in the original SurrealDB schema was intentional. The documentation comments added in FA-03 provide the only structure enforcement.

**Future option:** If structure enforcement becomes critical, PostgreSQL CHECK constraints with `jsonb_typeof()` or application-layer validation (`pydantic` models on write) could be added in a future phase. Not blocking for v6.0.

### DFR-04: WR-02 — No DB-level CHECK constraint on location_place_id

**Original issue (residual):** Cannot add `ASSERT $value IS NONE OR (SELECT entity_type FROM $value).entity_type = 'place'` because PostgreSQL CHECK constraints disallow subqueries referencing other tables.

**Deferred reason:** The only way to enforce this at the PostgreSQL DB level is a trigger function + trigger, which adds deployment complexity and potential migration issues for existing rows. The application code already enforces this constraint in both write paths. A DB trigger would be defense-in-depth, not a fix for a live bug.

**Recommendation:** Add a `CHECK (entity_type = 'place')` trigger if data corruption from bypassed app code is observed in production. Otherwise, the app-level check is sufficient for v6.0.
