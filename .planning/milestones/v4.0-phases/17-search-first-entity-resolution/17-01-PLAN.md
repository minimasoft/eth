<objective>
Implement search-first entity resolution: schema addition, LLM prompt/schema updates, new activity, and workflow/worker wiring.

**Purpose:** Replace the existing `resolve_entities_activity` with a search-first approach that queries existing canonical entities before calling the LLM — exact text matches skip the LLM entirely (~20-50% fewer LLM calls), and the LLM receives only candidate context for ambiguous matches.

**Output:** Modified files implementing the complete search-first entity resolution pipeline.
</objective>

  <name>Task 2: Create resolve_entities_with_search_activity with exact-match bypass, fuzzy candidate search, and LLM candidate resolution</name>
  <files>src/eth_pipeline/activities.py</files>
  <action>
    Create a new activity `resolve_entities_with_search_activity` in `activities.py` following the same structure as `resolve_entities_activity` (nullify-then-recreate, type batching, error dict returns). Place it after `resolve_entities_activity` (after line 532) and before the `create_event_canonical_entities_activity`.

    The activity signature: `async def resolve_entities_with_search_activity(document_id: str, result: dict) -> dict`

    Return shape: `{"document_id": ..., "resolved": N, "created": N, "skipped": N, "llm_calls": N, "exact_matches": N}`

    **Flow:**

    1. **Query + nullify (same as old activity):** Query all references for this document via events. Nullify `entity_id`, `canonical_entity`, and `resolution_confidence` fields. Use the same doc-level query scoping within the `async with get_db()` context.

    2. **Group by entity type** (same mapping: espacio→place, humanos→person, objetos→object, skip tiempo). Collect per-type references.

    3. **Fetch document context** (same as old activity — for LLM prompt fallback context).

    4. **For each type group, search-first resolution:**

        a. **Query ALL existing canonical entities** of this type globally (same query as old activity: `SELECT * FROM canonical_entity WHERE entity_type = $type`).

        b. **Import `unicodedata`** (stdlib, no dependency). Define an internal helper `_normalize(text: str) -> str` that returns `unicodedata.normalize('NFD', text).casefold()` for accent-normalized case-insensitive comparison. Per D-12 (NFD decomposition) and D-03 (case-insensitive).

        c. **Exact match pass:** For each reference, compare `_normalize(verbatim_text)` against `_normalize(entity["name"])` for each existing entity. If exact match found (entity name equals verbatim text after normalization), set `entity_id` on the reference to the matched entity's ID and increment `exact_match_count`. Remove this reference from the batch sent to the LLM. Per D-02, also set `canonical_entity` and `resolution_confidence` (1.0 for exact matches). Log at info level with reference count and entity ID.

        d. **Fuzzy candidate pass for remaining references:** For the remaining (non-exact-matched) references, build a candidate pool:
           - Query both directions of CONTAINS for each reference: `WHERE name CONTAINS $verbatim_text OR verbatim_text CONTAINS name` against the existing entities for this type. Per D-04 (bidirectional CONTAINS).
           - Deduplicate candidates by entity ID.
           - Cap at 5 total candidates per type batch. If more than 5 candidates found, take the first 5 sorted by name length (shortest names first — likely more generic/tighter matches). Per D-05 (up to 5 candidates).
           - Log candidate count: `"Search-first resolution [type=%s]: %d exact matches, %d references for LLM, %d candidates provided"`.

        e. **LLM call (if remaining references exist):**
           - Create OpenRouterProvider (same as old activity).
           - Call `provider.resolve_references()` passing remaining references and the candidate list as `existing_entities`.
           - The `_build_resolution_payload` now shows these as pre-filtered candidates.

        f. **Apply LLM results:**
           - For each resolution in the response:
             - `match_existing` with `matched_candidate_id` → set `entity_id` to the candidate ID, set `canonical_entity` and `resolution_confidence`.
             - `match_existing` with `matched_entity_id` → same (backward compat).
             - `create_new` → create canonical entity via `_create_canonical_entity()` helper, set `entity_id` and `canonical_entity` to the new entity.
             - `uncertain` → create tentative entity, set both fields.
           - Apply via `UPDATE reference SET entity_id = $eid, canonical_entity = $ce, resolution_confidence = $conf` for each resolution.

    5. **Logging and observability:** Per D-13, log candidate counts and LLM call savings at info level:
       ```
       "resolve_entities_with_search_activity completed [document_id=%s] [exact_matches=%d] [llm_calls=%d] [resolved=%d] [created=%d]"
       ```
       The `llm_calls` counter is the number of type batches sent to the LLM (can be 0 if all references had exact matches). The `exact_matches` counter records total exact-match auto-resolutions.

    6. **Error handling:** Same pattern as old activity — catch `ConnectionError` and broad `Exception`, log, return error dicts. LLM failures for individual type batches are caught and logged without blocking other types.

    **Per D-11 (nullify-then-recreate), D-02 (both entity_id and canonical_entity set), D-06 (search all types except event), D-07 (global search scope).**
  </action>

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-17-01 | Spoofing | exact_match bypass | mitigate | exact match comparison uses NFD+casefold normalization — entity name equality must be strict (no partial matching). Confirmed by unit tests in Plan 02 |
| T-17-02 | Tampering | entity_id UPDATE | mitigate | All SurrealDB UPDATE queries use parameterized bindings ($var), not string interpolation — SQL injection not possible |
| T-17-03 | Info Disclosure | LLM prompt candidate data | accept | Candidate entity names (place/person/object) are not PII; document context is already sent to OpenRouter in the existing activity. No new exposure |
| T-17-04 | Elevation of Privilege | activity returns | accept | Activity returns dict (resolved/created/exact_matches counts) — no sensitive data exposed through Temporal |
| T-17-SC | Tampering | NPM/Pip installs | mitigate | No new package dependencies required (unicodedata is stdlib, surrealdb and temporalio already present) — N/A |
