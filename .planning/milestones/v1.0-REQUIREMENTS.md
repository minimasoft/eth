## Validated

### R001 — System accepts document blobs in any format, stores the original, and tracks processing status (pending, extracted, processed, failed)

- Class: core-capability
- Status: validated
- Description: System accepts document blobs in any format, stores the original, and tracks processing status (pending, extracted, processed, failed)
- Why it matters: Documents are the primary evidence source; preserving the original in any format is the foundation for auditability and future processing
- Source: user
- Primary owning slice: M001/S01
- Validation: S01 validates: SurrealDB document table defined with SCHEMAFULL enforcement, status lifecycle (pending/extracted/processed/failed), and field for storing original blob and text content. Schema applied and verified via GraphQL introspection.
- Notes: First version handles plain text; blobs in other formats are stored until a text extraction transform is available

### R002 — Plain text is extracted from ingested documents and stored alongside the original

- Class: primary-user-loop
- Status: validated
- Description: Plain text is extracted from ingested documents and stored alongside the original
- Why it matters: LLM extraction and event analysis operate on text; extracted text is the audit trail between original and events
- Source: user
- Primary owning slice: M001/S01
- Validation: S01 schema defines text_content field on document table (SCHEMAFULL). S02 ingestion API (POST /documents) stores submitted text in SurrealDB with document_id and status=pending. Verified by verify_s02.py check 8 (full integration: POST → SurrealDB confirms stored). S03 verify_s03.py check 9 confirms GET /documents/{id} returns document with text_content.

### R003 — LLM extracts structured events from document text, outputting space (verbatim place reference), time (start/end timestamps), humans (verbatim person reference), objects, and qué-pasó (free-text what-happened)

- Class: primary-user-loop
- Status: validated
- Description: LLM extracts structured events from document text, outputting space (verbatim place reference), time (start/end timestamps), humans (verbatim person reference), objects, and qué-pasó (free-text what-happened)
- Why it matters: Core value proposition — turning unstructured legal text into structured, queryable events
- Source: user
- Primary owning slice: M001/S02
- Validation: S02 defines EVENT_EXTRACTION_SCHEMA as strict JSON Schema with additionalProperties:false, requiring espacio/tiempo/humanos/objetos/que-paso fields and verbatim references, validated. S03 DocumentProcessingWorkflow chains extract_events_activity with retry (max_attempts=3). Full pipeline verified end-to-end (POST→Temporal→SurrealDB→GET events). Note: POPULATED event content requires OPENROUTER_API_KEY; structural pipeline proven without it.

### R004 — Events store extracted verbatim references as first-class entities: espacio (place name, address, GPS coordinates), tiempo (start/end timestamps), humanos (person name/description), objetos (identifiable objects like vehicles). Each reference records its exact text from the source document plus its type

- Class: core-capability
- Status: validated
- Description: Events store extracted verbatim references as first-class entities: espacio (place name, address, GPS coordinates), tiempo (start/end timestamps), humanos (person name/description), objetos (identifiable objects like vehicles). Each reference records its exact text from the source document plus its type

- Source: user

- Validation: store_extraction_results_activity creates event records with espacio/tiempo/humanos/objetos fields and reference records with exact text and type — verified by integration test in verify_s03.py (check 9: POST→GET events→DELETE→reprocess).

### R007 — Every event must be traceable through a full chain: original document blob → extracted text → LLM extraction output → resolved entities. Each step records its source and timestamp

- Class: continuity
- Status: validated
- Description: Every event must be traceable through a full chain: original document blob → extracted text → LLM extraction output → resolved entities. Each step records its source and timestamp
- Why it matters: No black boxes — errors must be traceable to their source for correction and accountability
- Source: user
- Primary owning slice: M001/S03
- Validation: DocumentProcessingWorkflow chains: update_document_status(processing) → extract_events → store_extraction_results → update_document_status(processed). Each step records timestamp via updated_at. Status and error_message are persisted in SurrealDB for traceability — verified by integration test (check 9 confirms status=processed after pipeline run).

### R008 — When LLM output is identified as incorrect, the bad extraction results can be deleted and the document reprocessed via workflow replay, producing new results from the same source text

- Class: operability
- Status: validated
- Description: When LLM output is identified as incorrect, the bad extraction results can be deleted and the document reprocessed via workflow replay, producing new results from the same source text
- Why it matters: LLM outputs will be wrong sometimes; the system must support correction without re-ingesting the document
- Source: user
- Primary owning slice: M001/S03
- Validation: DELETE /documents/{id}/events endpoint clears events+references and resets status to pending. Temporal workflow ID conflict policy USE_EXISTING enables safe replay on re-POST. Verified by integration test (check 9: POST→DELETE→rePOST creates fresh results).

- Description: LLM provider is abstracted behind a common interface. OpenRouter is the first implementation. The interface accepts prompt, output schema, model hint, temperature, and max_tokens

Provider swap requires only replacing the implementation class.

### R010 — All document processing is asynchronous via Temporal workflows. Activities are retriable with exponential backoff (up to 10 attempts, spreading across the day). The pipeline is replayable — workflow state persists across restarts

- Class: operability
- Status: validated
- Description: All document processing is asynchronous via Temporal workflows. Activities are retriable with exponential backoff (up to 10 attempts, spreading across the day). The pipeline is replayable — workflow state persists across restarts
- Why it matters: Durable processing ensures documents are not lost on failure and processing automatically continues when dependencies recover
- Source: user
- Primary owning slice: M001/S01
- Validation: S01 validates: Temporal worker stub registers task queue 'event-extraction' and connects to localhost:7233. Docker Compose runs Temporal Server (port 7233) with health checks. Worker import verified working. Activities/workflows stub classes defined for retriable execution.

### R014 — Canonical entities (places, persons, objects) accumulate verbatim references over time as new documents are processed. Each reference records its source event and document

- Status: validated
- Description: Canonical entities (places, persons, objects) accumulate verbatim references over time as new documents are processed. Each reference records its source event and document

### R015 — Canonical entities can be merged (two entities are actually the same) or split (one entity conflates two distinct references). References are rewired accordingly — moved between canonical entities without losing provenance

- Class: operability
- Status: validated
- Description: Canonical entities can be merged (two entities are actually the same) or split (one entity conflates two distinct references). References are rewired accordingly — moved between canonical entities without losing provenance
- Why it matters: Entity resolution is iterative and imperfect; the system must support correction as understanding improves
- Source: user
- Primary owning slice: M002
- Validation: scripts/verify_s03_m2.py 10/10 checks pass. Merge endpoint rewires references and soft-deletes absorbed entity via superseded_by. Split endpoint partitions references across new entities with split_from provenance. All validation conditions covered: self-merge (400), cross-type (400), non-existent entities (404), already-merged (400), empty partitions (400), duplicate reference IDs (400), invalid type (400), non-existent reference IDs (400), references not pointing to source (400). End-to-end happy paths verified for both merge and split operations.
- Notes: S03: Merge and split endpoints implemented and verified. Merge rewires references to survivor with resolution_confidence=1.0 and soft-deletes absorbed entity via superseded_by. Split creates new canonical entities with split_from provenance tracking and partitions references by name group. Full end-to-end validation with GraphQL verification pending S04 integration tests.
