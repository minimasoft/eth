## V7.0

### Recap

Finally the document processing pipeline and interface are mature. The full process is visible end to end with details and it's possible to get costs, times and prompt detail. With this it becomes evident the current references/entities system is not good enough.

### Clean-up 

We will remove references, events, entities to redoit from scratch based on what we learned so far. Carefully remove activities without breaking the existing good things like document logs, llm logs, cascade delete, simple UI. We also keep working patterns, i.e. big documents are divided in parts to allow standard prompting with reasonable context lenght (favors caching of the beginning of the prompt/instructions). 

### Principles and goal

This tool will be used to transform spanish legal documents and evidence into data points for futher analysis, discussion and communication. The kind of cases analyzed are very severe, humans right violations, war crimes, genocides, etc. This could trigger some LLM safety mechanisms which is expected but can be prevented. The tool goal is to transform court documents and evidence into data that is easy to think about and visualize helping us avoid the errors from the past and anchor different points of view in the existing facts and evidence.
This is important to mention in the LLM prompts to avoid triggering safety mechanisms that may find it hard to repeat what's found in this documents and evidence forgetting it's actually helping to prevent it.

### Past lessons

The reference + entities/events system was not good for the LLMs, not clear enough and not good for UI neither. We will make a composed object that is easier to reason for the LLM and better for the UI. References will be embedded in the main event object, all previous schemas are deprecated and ignored.

## Parts processing

We need to use the parts/chunks properly. Document is partitioned FOR llm processing and easier references in big documents. So whichever partition we do in the pipeline is then the parts for the LLM to process and mention/log progress. We will target a max 240k token context and prompts that maintain the beginning static when possible to favor caching. We avoid hitting the 240k limit so target max 512kb chunks configurable and smart partition. Divide when it's a known place (i.e. punctuation+space hints if found) If we need to divide 600kb into 512kb max chunks we divide by approx 2 300kb chunks and not a 510kb and a 90kb chunk. Each successful part should commits its events so those have an id and reference to the document and can be used in the next part prompt and then refrence by id by the LLM.  

## SQL refactor

The sql refactor will be massive, we can start from scratch (new db name maybe and drop the old one) it's important to keep good track of document and event relations (and all other relations). The json describes a unified object but IRL in the db we will want to easily link participants, locations, events and documents. The vectors are clearly N-N relations that need to be indexed and easily used. We base in pgsql.
